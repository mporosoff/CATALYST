# Desktop components and verification

Run with Python 3.12+ and Tk installed: `python -m pip install -r requirements-desktop.txt`, then `python -m catalyst_desktop`. Python.org Windows and macOS installers include Tk. Linux additionally requires a graphical desktop and the platform Tk package.

`catalyst_desktop/model.py` owns in-memory source snapshots, deterministic decimal unit/name mappings, required context, toolkit bundle integration, immutable revision encoding/digests, and explicit approval. It reuses the bounded `catalyst_ingest` readers. No spreadsheet formula, macro, or AI processing executes. Source-version, entity, modality, and format are part of mapping identity. Mapping documents and their digests are embedded in saved revisions.

`catalyst_desktop/scisure.py` owns direct authenticated HTTPS, explicit server-origin/API-path validation, redirect rejection, TLS verification, bounded responses, paginated reads, and unsigned destination validation. The sandbox is the default, and users may enter another HTTPS DNS origin on port 443. Origins cannot include user information, sign-in paths, queries, fragments, IP addresses, or a nonstandard port. The client binds requests and destinations to the selected origin and never forwards a token through redirects. It does not use an environment-provided HTTP proxy. Token text and remote error bodies are never included in displayed errors or repr strings. HTTP 401 and 403 have distinct guidance; HTTP-date and numeric Retry-After values are bounded.

`catalyst_desktop/credentials.py` selects the native Windows, macOS, or Secret Service keyring implementation explicitly. It does not accept third-party plaintext/cloud fallback keyrings. Credentials are keyed by normalized server origin, retaining compatibility with the existing sandbox key. Credential storage is optional and failure leaves the user able to work with a session-only token. The GUI clears the token and remote state when the server changes.

Connection guidance follows the supplied eLabNext REST API Quick Start Guide: create a server-specific token in **Apps & Connections → Manage Authentication**, including after university SSO/SAML or two-factor sign-in, then paste the raw token into CATALYST. The client adds the `Authorization` header. Connecting and inspecting a destination are read operations; they cannot establish permission for later section, file, sample or schema writes. No authentication endpoint for a university password is needed in the desktop app.

`catalyst_desktop/publication.py` verifies revision approval, lineage/context consistency and source hashes, creates a revision-specific FILE section (also reads legacy FILES), stores the review manifest, uploads originals, verifies every byte by SHA-256, and writes a completion receipt last. It checks destination status before writes. Ambiguous outcomes never trigger blind automatic retries. Definitive request rejections remain manually retryable; a successful write followed by failed verification remains unknown. Duplicate remote names and conflicting profile versions are rejected. Profile-version checking scans CATALYST packages visible across the active group, including legacy profiles. SciSure does not provide an atomic registry through this implementation.

Publication also rechecks catalog conflicts during a transfer, reads back the completed packet and originals, and verifies that the revision section and attachment snapshot stayed consistent. Numeric API IDs are normalized across string/integer response forms. Canonical destination ownership remains binding when display names change; retries reuse the saved approval and destination envelope. Manifest-less revision sections reserve their IDs and cannot silently be duplicated in another experiment.

`traceability.py` owns the six-lab registry and dispatches the legacy traceability schema and the adaptive `catalyst-traceability/2` schema. `workflow.py` defines the adaptive record types, relevant fields, and validation. Adaptive contexts declare `workflowVersion="2"`; their review preview uses `catalyst-desktop-review/3`. Legacy previews remain readable and retain their original requirements. Generated IDs include the creating lab and record type, including `PRC` for versioned procedures. Every mapped row remains bound to one declared subject; conflicting mapped labels block approval.

The adaptive flow separates procedure definitions, sample registration, synthesis executions, measurements and computations. A standalone procedure records its name, type, technique, version and instructions/reference/attached-file hashes. A sample registration records its original description and optional state/parent. A later measurement or synthesis carries a `sample_ref`, not a re-declaration of the original material. Its dataset method identifies the reusable procedure version. Selected sample/method references preserve exact source revision IDs and SHA-256 digests. Synthesis records declare the actual execution separately. Computations retain their model definition and optional physical relationships. Original-file preservation is the default; standardized conversion is an explicit choice. Metadata-only procedures, samples and synthesis executions use `data_status=metadata_only`, have no dummy source artifacts, and still require an immutable reviewed revision.

`catalog.py` reconstructs the shared in-memory library from CATALYST review packages visible across the active SciSure group. It rejects conflicting saved definitions, checks completed parent/model relationships and exact selected source revisions, and reserves IDs from incomplete packages. Standalone procedure reviews are valid catalog entries without a material/model subject. Referencing measurements contribute aliases and dataset links to the original sample entry. Incomplete reads or more than 250 reviews fail closed. No manifests or research data are cached on disk.

`library.py` supplies search/filter choices and minimal selected-reference contexts. Sample labels do not collapse distinct canonical IDs. Procedures can be searched by name, ID, version, lab, type and technique; exact duplicate definitions retain their source reviews. Legacy embedded synthesis procedures with a document reference can be reused, but bare historical measurement method IDs do not constitute registered procedure evidence. Queued definitions are labeled, preserve their source revision hashes and must be saved before dependent records.

The separate native protocol loader calls the documented read-only `/api/v1/protocols?scope=group&groupIDs=...` and `/api/v1/protocols/version/{protVersionID}` routes. It accepts finalized, nondeleted versions visible in that group scope, including shared protocols owned by another group, and rechecks exact IDs and snapshot consistency. It returns the native details, content snapshot digest and exact version URL. The researcher must classify the method type and technique before staging a CATALYST registration. Native-backed registration IDs derive deterministically from the tenant/protocol identity with a lab prefix; protocol version remains separate. This loader never creates or publishes a native protocol. Procedure instructions and references remain in CATALYST experiment packages; native inventory writes have a separate explicit review path.

`integration.py` performs a separate read-only setup inspection. It retrieves actual sample type/metadata IDs, required fields, quantity settings, account permissions, experiment collaborators, and optionally an exact sample and protocol version. It never executes a metadata validation script, creates a field/sample, or changes roles. It does not turn self-reported procedure references into validated native links. `tests/test_api_contract.py` covers these contracts with synthetic endpoints.

`configuration.py` defines CATALYST Material v2 and six typed metadata fields. Canonical ID, creating lab, description/composition and schema version are required; the app supplies all except the description. State and parent are optional. Its read-only planner discovers native IDs and conflicts; the separately approved installer adds only missing schema records with primary/active-group checks, stale-plan rejection, read-back verification, and persistent in-session uncertain-write guards. Existing Material v1 schema and research samples are retained, not migrated or overwritten. `docs/scisure-configuration.md` describes additive setup and migration boundaries.

Adaptive native inventory is explicitly requested by `inventoryMode="native"`; an absent flag retains experiment-package behavior for existing reviews. Eligible records show **Also register / link this sample in LIMS inventory**. Connected new samples and selected native samples enable it by default. **Search LIMS** / **Choose existing LIMS inventory sample…** search native samples and prepare an exact selected reference for review while preserving an unfinished draft. New native samples need the v2 setup; reuse of an existing verified native sample does not require changing its type or metadata. A connected, verified destination is required to prepare the native plan. The immutable review includes sample creation/reuse and applicable Used/Generated links, and publication validates and reads back those planned operations. Computations stay distinct from physical inventory; native protocol creation is not part of this path. Schema installation alone does not authorize a research write.

Uninterpreted sources use artifact format `binary`, explicitly recording that no parser ran. The image/native file route preserves bytes, including embedded metadata, without decoding, rendering, executing, or converting the file. `raw_only` reviews carry `data_status=original_files_only`, no mapping, no standardized rows, and a prominent warning. Adaptive original-file measurements require their sample/method links, date and operator; run-specific details remain optional. Mapped data additionally requires the units/basis necessary for the selected conversion, and toolkit import requires processing evidence. Imaging acquisition and scale information can live in the reusable method with run-specific deviations recorded in notes. No new runtime dependency is needed.

Paged reads use `totalRecords`/`maxRecords`, not the samples-only `hasNextPage` shortcut. The API maximum is 1,000 results **per page**; CATALYST separately caps one loaded list at 1,000 total records. Neither is an API-wide database limit. Inconsistent totals, short pages, repeated records and the application ceiling fail closed. GET 429 responses receive at most two retries with bounded `Retry-After` waits; POSTs are never automatically retried. Same-name Office revisions are displayed with file ID, previous file ID, and stored date. Native embedded-image/legacy section endpoints are not yet included in attachment browsing.

The review manifest explicitly says `prepared`; the completion receipt is a separate record. `history` and `read_review` support read-only access to signed experiments and return no new disk files. Downloaded original bytes are verified before reuse. Checksums establish integrity consistency, not a cryptographic identity signature. With shared tokens, client-entered names cannot supply independently enforced reviewer identity or partner isolation.

`exports.py` supports explicit user-selected saves. A review ZIP requires a complete validated receipt and every original's verified bytes. It includes the approved review, mapping/context/provenance, receipt, standardized JSON, an optional CSV convenience view, and original files. Toolkit quantities become CSV columns labeled with field and unit; exact decimal text is retained and column collisions fail explicitly. Text that could execute as a spreadsheet formula is escaped in CSV only; exact JSON/originals retain the full evidence. Standalone attachment downloads recheck section membership and metadata. Saves stage a complete file in the chosen destination directory before replacing the requested path; failed writes preserve an existing destination. There is no automatic download folder or research-data cache.

`design.py` defines the local visual system: colors, typography, original program-drawn icons, scalable rounded button surfaces, visible focus/disabled states, cards, narrow scrollbars, and explanations shown on hover or keyboard focus. It adds no runtime dependency, web renderer, remote font, network asset, or AI feature. `gui.py` retains the shell, connection, review, saved-record access and legacy review editor. `workflow_gui.py` owns the adaptive form, default measurement/XRD choice, record-type selector, search-driven sample/method links, original-file default, optional mapping and batch integration. Adding a missing linked sample or procedure uses an inline dialog, stages an unapproved definition, and preserves the active draft; native version references are handled with the same binding rules. Hidden generated identifiers and provenance fields stay in the context without requiring manual transcription. Visible required fields are grouped, marked with an asterisk and accompanied by a completeness count; scientific validation remains separate.

`batch.py` owns a bounded memory-only queue: at most 50 records and 200 MiB including original bytes, parsed representations and review content, while each record retains the ordinary six-file/20 MiB per-file/40 MiB total limits. Each queue item binds a revision, its exact source snapshot and a separate approval. `batch_gui.py` supplies review/edit/remove/reorder controls and explicit sending. Batch file import creates one original-file measurement per selected file only after confirming that sample, method, date and operator apply to all selected files. Multi-file runs, mapped tables and toolkit bundles are staged as individual grouped records. Queued definitions must precede records that reference them, and changing a definition leaves old dependent pins invalid until relinked and reviewed. Publication sends approved items sequentially, preserves completed status and stops on the first failure; uncertain records require reconciliation and are not silently retried or duplicated. Editing a record clears its approval. Closing the app discards unsent queue state.

`help.py` supplies step-by-step upload and access/download guidance in a resizable, nonmodal help pane. It explains choosing a record type, reusing or adding definitions, preserving originals, optional conversion, batch review and per-record approval. Its actions only navigate workspace pages, including Batch review. Help does not upload, download, approve or modify research data.

The native Tk GUI uses a single worker thread for parsing/network operations and locks editable controls while an operation runs. The UI never passes Tk calls to the worker thread. It stores no research state in a local database. Unknown-write guards remain in application memory across token reconnect/destination re-verification. Closing an incomplete in-memory review discards that state; restart recovery requires manual remote reconciliation. Cross-process concurrent writes to the same revision cannot be made atomic by the client; duplicate/conflicting remote records stop the workflow for owner review.

## Tests and builds

The 0.8.0 audit extends the earlier bounded saved-review/approval checks and strict JSON parser. JSON numeric tokens and processed-workbook settings retain exact source precision; cached formula results never become raw observations. Formatting-only spreadsheet cells no longer block valid tables. Toolkit imports flag inconsistent row roles, missing selected results, impossible values, and embedded formulas. Stored normalized values, subject labels, toolkit results, and nominal time axes are checked against their declared bounds and preserved review evidence.

The focused regression suites include `test_data_audit.py` (source/scientific consistency), `test_transport_audit.py` (server/token/API/setup boundaries), `test_publication_audit.py` (transfer/catalog/configuration consistency), `test_procedure_library.py` (searchable definitions, exact reference pins, immutable sample reuse, native protocol version reads and a synthetic register-then-measure round trip), `test_batch.py` (review boundaries, source snapshots, dependencies, limits and stop-on-failure), and export tests. Existing robustness, lineage, modality and configuration suites remain. See [the historical 0.8.0 audit notes](desktop-audit-0.8.md) and [current integration scope](scisure-integration-review.md). These are synthetic tests; no authenticated live SciSure verification is claimed for the adaptive workflow, batch sender, native inventory or native protocol reader.

Before building, update the isolated installer with `python -m pip install --upgrade pip==26.2.1`. After installing the build requirements, run `python scripts/audit-desktop-dependencies.py`; it checks public installed distribution names/versions against PyPI and writes an ignored report. It is never imported by the desktop runtime. CI blocks packaging on a vulnerable or incompletely checked dependency set and retains its report in build artifacts.

Release packaging requires **Python 3.13.15** on Windows and Mac, enforced by both the workflow and packaging script. This avoids silently bundling an older cached 3.12 interpreter. The packaged application includes Python; teammates do not install it separately. Compatibility tests may still run locally on a patched 3.12 interpreter.

- `python -m unittest discover -s tests -v`: synthetic scientific boundaries, source precision/preservation, native transport security, approval, upload/read-back, corruption, and lost-response recovery. No live credentials or research data.
- `python scripts/test-desktop-gui.py`: real wheel events over fields/selectors, high-resolution wheel accumulation, minimum-window layout, the single required-fields panel, conditional markers and optional-field placement, hover/focus explanations, next-missing-field navigation, help steps/actions, dynamically rebuilt context, native result scrolling delegation, mode-dependent mapping visibility, persistent review action, release link, schema plan/application, selection, mapping, preview, approval, and invalidation. No network or credential store calls.
- `python -m pip install -r requirements-desktop-build.txt` then `python scripts/build-desktop.py`: package on the target operating system. Outputs go to ignored `desktop-dist/`; only code, Python dependencies, and public mapping definitions are included.
- `python scripts/test-workflow-gui.py`: adaptive record forms, preserved add-new drafts, reusable links, original-file handling, optional conversion, batch editing, per-record approval and an ordered synthetic transfer. `test-batch-gui.py` and `test-tooltips.py` check the batch controls and hover/focus guidance. No live credentials or network calls.
- `python scripts/test-native-inventory-gui.py`: reviewed native sample creation and reuse, inventory search, preserved linked drafts, minimal metadata, batch transfer and native experiment links. Run GUI scripts sequentially so their focus checks do not compete. `test_inventory.py` and `test_inventory_publication.py` cover native API contracts, stale plans, unknown writes, receipts and downloads.
- `.github/workflows/desktop.yml` builds Windows and macOS packages using synthetic data only, with no repository secrets. GitHub Releases distributes direct EXE/DMG assets; Actions artifacts are internal build archives. Windows uses PyInstaller one-file packaging and is additionally tested after copying the EXE alone into an isolated folder. Mac uses app bundles in verified DMG images. These development builds are not publisher-signed or Apple-notarized.

The legacy Sites web application is retained as historical source and is not the desktop runtime. Do not deploy it as the solution to the current requirements. The earlier hosted prototype and its saved credential still require retirement through the owner’s platform controls. No decommissioning or token revocation is claimed by this desktop change.


## Sample workspace 0.11.0

`sample_workspace.py` provides native/catalog identity merging, sample-centric records, exact native Used/Generated membership, readable saved-record details and verified downloads. `runs.py` / `runs_gui.py` implement reviewed project/study/experiment creation, fresh scope checks and unknown-write guards. `publication_destination` is an optional additive field on v3 reviews: new connected previews bind it, and Publisher refuses a different target; old envelopes retain their original behavior. BatchQueue preflights publisher routing before starting any writes. `issues_gui.py` maps validation issues to the actual draft controls and loads a batch item for editing before navigating. Internal codes remain in the immutable validation evidence, while user-facing guidance uses meaningful labels.

`sample_documents.py` / `sample_documents_gui.py` handle native FILE attachments independently of experiment packages. A narrowly validated sample-FILE POST creates a new sample-local document group under a stable reviewed UUID key, with no `sampleTypeMetaID` and only newly uploaded file IDs. It never replaces existing attachment lists or changes shared sample types. The path verifies uploaded bytes and readback, checks scientific identity, and retains unknown-write guards. Managed document-group fields (and the earlier fixed CATALYST_documents field) are excluded from scientific identity snapshots; other identity metadata retains existing validation. External hybrid storage is unsupported.

Additional focused suites cover run creation, multi-run reviewed publication, sample workspace attribution, direct sample documents and error navigation. Run all native GUI scripts serially using the release interpreter. Automated tests use synthetic in-memory services; real sandbox write/read acceptance still requires the user's authenticated app session.
